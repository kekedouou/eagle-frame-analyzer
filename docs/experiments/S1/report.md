## 实际 FFmpeg 结果

最终整轮是新缓存构建，未清除 Windows 文件缓存，因此不能称为操作系统冷启动；合成输入的耗时包含首次生成输入文件。

| 输入 | 帧数 | Node 首次准备 | 解码音频相对视频起点 |
| --- | ---: | ---: | ---: |
| H.264 CFR，3 秒 | 90 | 697.0 ms | 0 |
| H.265 VFR，4 秒 | 56 | 1116.6 ms | +0.178 s |
| VP9 无声，2 秒 | 60 | 694.5 ms | 无音频 |
| 原 B 专用 VP9，3840×2160 | 828 | 7848.3 ms | +0.0065 s |

原素材 SHA256 与授权身份一致，准备前后均核对；源文件只读。原媒体终点取索引/音频为 13.82 秒；旧 B 的容器长度记录为 13.821 秒，二者口径不同，未覆盖旧报告。音频为原双声道、48kHz float WAV，5,304,486 字节、13.8135 秒。JPEG 共 21,203,659 字节，q=3 仍是实验选择。

- 原视频生成环节 7388.2 ms、Node 总准备 7848.3 ms。早一轮未加入 FFmpeg RSS 采样的 Node 总准备为 7154.5 ms，分开保留，不混算。两者都缺少浏览器音频初始化与首帧绘制，不能判定 P-03 通过。
- 三段合成输入的 **206 个作者预期时间戳**全部吻合；每段首、中、末共 **9 张 JPEG**经独立 FFmpeg 灰度解码，实际画面条码吻合。不是所有图片逐像素检查，也不是 Eagle 画布检查。
- VFR 按实际 PTS 查帧，边界前后及首末定位通过。PTS 是帧在媒体时间轴上的显示时间；没有用平均帧率推算 VFR 索引。
- 缓存完整校验/复用、越界资产拒读、预先取消、首帧后取消及等待子进程退出后清除 partial、含未知文件时整个清理拒绝，均通过。

最终整轮 runtime 文件字节 29,467,579（28.10 MiB），当时历史证据另计 30,965 字节；写入本轮报告及后续证据后略有增加。总产物配额 512 MiB，分为 runtime 480 MiB / evidence 32 MiB；单证据 8 MiB。计文件字节，不含文件系统簇开销，未实际写满配额测试。

FFmpeg 每秒采样 7 次，观测工作集峰值 **168.54 MiB**；整个 Node 检查每 100ms 采样峰值 **76.19 MiB**。短任务来不及采样时记 `null`。采样会漏峰值；不同进程峰值不能相加冒充同时总峰值，均不包含实际浏览器/GPU。播放器 512 MiB 只约束已登记缓存数据及在途预留，不保证进程总内存小于 512 MiB。

## 实现入口与失败排查

文件职责复用 [计划](plan.md#最小文件职责与运行顺序)，不另建架构报告。核心入口是 `app.js` 的 `initialize()` → `prepare.cjs` 的 `prepare()` → `player.js` 的 `load()`；播放经 `play()` 和每次浏览器刷新机会 `_tick()`，最终 `_draw()` 提交画面。

FFmpeg 在一次源视频解码链上输出 JPEG、帧时间索引，并单独提取音频；Node 通过管道接收并限额写入。JPEG 是压缩图片，播放/拖动时仍需读取、解压为像素；已解码图像暂存在有上限的 RAM 缓存。正常播放以 Web Audio 音频输出时间估计选择画面；拖动/逐帧先停声，并在绘制前核对当前样本和最新目标。无声视频使用单调时钟。

准备失败先查 `prepare.cjs` 的工具路径、限额、FFmpeg 退出和 PTS/JPEG 数量；已就绪但定位错误查 `player.js` 的帧索引、请求及 draw 条码；控件或保存问题查 `app.js`。时间轴数字正确不代表实际像素正确。

修正与边界：

- 两次合成器失败定位为 MP4 容器时间设置问题，最终使用 `delay_moov` 并去除 `negative_cts_offsets`，保留 B 帧。不能通过硬改作者预期值使测试通过。
- H.265 作者音频相对起点 +0.2 秒，解码首时间实际 +0.178 秒，含 AAC 预滚；记录解码后首 PTS，不把音频和视频分别归零。WAV 的 RIFF/data/fact 长度已修补及检查；Chrome 108 实际解码仍待验证。
- 已修正网页与 CommonJS 并存时的导出、播放画面提交后的 UI 通知、音频解码 Promise 拒绝处理、切换前证据快照。没有改动 A/B 来迁就 S1。
- 拖动脚本每轮重置已解码 RAM、使用相同目标序列，再分别注入 0/25/60ms 解码延迟；磁盘和系统文件缓存未清除。记录输入、有效目标、就绪、提交、过期/未完成请求和最长无提交间隔。
- 严格最新目标在持续慢解码下可能没有画面更新；模拟如实重现，同时最终目标能达成。正常播放超过 150ms 缺画面时会停声并提示 UNDERRUN；这只是实验保护，不是放宽 P-01/P-02 或宣布解决饥饿。
- 绘制提交和 rAF 刷新机会都不是物理屏幕呈现。脚本提交率、完成请求 P95 必须结合丢弃请求和间隔解读；物理声画误差留空。
- 窗口首次计时从 Eagle 的 `onPluginCreate` 回调进入开始，包含本实验初始化；无法覆盖 Eagle 在回调前创建窗口/解析脚本的时间，不冒充用户点击插件起的完整启动延迟。

## 用户真实 Eagle 验收步骤（待执行）

1. 在 Eagle 开发者项目中手动加载 **`prototypes/playback-clock/manifest.json`**。这是新的 S1 原型入口；旧 `window-player` 不承担本实验。启动自动准备 H.264 样本，成功时停在第一帧；下拉样本是实验控件，S1 不跟随 Eagle 当前选中素材。
2. 播放 H.264，观察约 1 秒处白闪与提示音；暂停、拖动、逐帧并恢复，观察声音是否停止及最终画面。再选择 H.265 VFR，观察约 1.2 秒处白闪/提示音；VP9 无声样本应正常操作且不要求音频。
3. 选择“原 B 专用”样本；如需测首次完整等待，先点击“清理 S1 生成素材与缓存”，再“重新载入样本”。检查记录 `reused:false`；自动准备耗时包含浏览器阶段，不能用 Node 时间替代。清理保留 evidence，原素材不变。
4. 运行约 10 秒拖动测试，人工快速往返拖动、松开、逐帧及播放/暂停，观察错误提示。默认核对画布帧标记会增加像素读回成本，证据记录开关；原素材没有独立条码，不虚构核对结果。
5. 填写“人工观察”，点击“保存本次证据”。自动脚本也会保存新 JSON，但不替用户填写判断。需要检查生命周期时，可在准备中取消/切换样本、关闭后重新打开；必须记录是否实际执行。

清理入口只验证并删除 S1 runtime 已知文件；含未知内容时拒绝操作，不删除证据。关闭事件无法保证等待异步收尾，意外退出的孤儿 FFmpeg 恢复、正式跨进程缓存锁尚未实现。

## 执行与判定

1. 固定代码/工具版本、输入 SHA、源规格、实际缓存路径、预算、独立预期和环境；先执行无媒体副作用的单元/模拟检查。
2. 在隔离新缓存进行实际 JPEG/PTS/PCM 准备，前后核对源 SHA。三段编号帧依作者预期检查全部206帧；原视频采用另一路独立参考核对至少100个位置及首末帧，不把内部索引自洽当作画面正确。
3. 宿主性能严格沿用 verification：正常快速拖动3×30秒、独立随机定位3×200、未命中解码注入0/25/60ms各3轮；固定种子 `0x4e564130`，目标混合往返/反转/随机，输入约120次/秒。记录每个原始输入及合并/取代/取消/失败/未完成，终点仅为画布提交，屏幕物理呈现未测。
4. 每轮30秒之后释放定位最多等待5秒，清空在途任务最多等待10秒；超时保存失败与悬挂任务，不记为成功或零延迟。0ms常态按≥55次/秒、最长无提交≤100ms、P95≤50ms判定；压力轮只检查准确、安全、有限结束并如实报告性能。
5. 真实窗口首次准备3轮、完整缓存复用3轮，从加载回调开始至完整可操作；本地准备耗时仅是分段数据，不替代 P-03。用户观察快速拖动、首末及逐帧、声音；未完成不得自动填写人工通过。

首次反馈后的重测只要求“复测正常拖动”（同种子0ms 3×30秒、独立随机3×200）及用户选中有声视频的人工拖动/播放；不默认重跑已取得的准备与编号检查。日志使用 compact-v2：聚合重复状态/取代通知，保留每次原始输入、请求身份、真实读取/解码完成、绘制和终态，时间戳不取整；仍按12MiB估算内存、16MiB单文件、128MiB总证据限额。运行前正常重测预留40MiB、完整协议预留100MiB；不足时拒绝，不删除旧证据或增额。

新调度在输入及槽位释放时立即开始最新图像工作，绘制仍仅在浏览器提供的下一次绘制机会执行；持续拖动暂不预取无关邻帧，释放后恢复，最多2真实在途/1最新待目标及512MiB不变。新增read/decode分段时长；读取时长包含路径、身份、SHA检查，不据此单独声称hash耗时。人为25/60ms现模拟已进入解码器的不可取消服务（v2），旧版在等待后可取消并几乎不填缓存，故新旧压力轮不能直接作为性能改善倍数比较；旧原始记录保留。

人工144Hz连续输入进一步暴露相位饥饿后，当前修复候选在上述边界内增加**一个拖动方向预测帧**：最近连续、方向相同的时间变化用于预测下一位置，仍按实际PTS映射；最新真实目标先取得任务位置，有空余才准备预测图像。预测不成为定位请求、不取得绘制权限；反向、长时间无输入及释放后不延续旧预测，过时读取可在进入解码前停止，已进入的真实解码等待结束。总在途仍最多2，数据仍受512MiB预算，绘制仍只在rAF同步核对最新目标。该选择落实已有有限前取，不改变JPEG方案/产品需求；不是无论任何输入都已跟手的保证。

当前证据约剩15.89MiB，40/100MiB自动协议不能运行，也不能降低其预检冒充整组复测。修复本地检查后先由用户做**一次不超过10秒的定向人工拖动并保存一次**：重新打开当前T0窗口、沿用同一4K素材，快拖和快速反向，释放看最终位置；不点击性能/准备/编号协议。仅检查此次修复是否值得继续，不能代替3×30秒正式关卡或v2压力覆盖。实际保存仍受128MiB总额及16MiB单文件限制，失败不覆盖旧证据、不增额、不清理；之后按实际剩余容量规划完整复验。人工字段只要快拖明显卡顿就不能填“跟手”；未检查的声画等留未检查，不从此前反馈自动填入。

自动检查可修复的问题持续推进；必要宿主测试处暂停提交可运行入口和最少操作说明。T0 尚未通过时不铺开 T1。失败记录保留，只有证据显示需变更批准架构时才提出变更；不降低门槛。Git 保存代码/本地检查版本，真实关卡获验收前不建立 `phase4-t0-verified` 标签。

### 待审定向对照：固定512MiB，区分读取与提交时机

2026-10-11用户在理解两项区别后明确“懂了，批准”，授权以下两项定向对照的实现、本地验证和用户宿主复验；**这是试验授权，不是选定新的正式架构**。简单扩大预测窗口/平滑输入的探索没有稳定收益，不继续盲调；全1490帧解码常驻需约5.116GiB，也不提高预算。

- 基线：当前JPEG、最多2任务/1最新目标、512MiB、仅rAF提交。
- 候选一：把一部分512MiB分给经过校验的压缩JPEG内存池，仍保持原画质、实际PTS及仅rAF提交。本素材JPEG总量60.87MiB，理论上解码工作集由143张降至约125张，可省去部分读取，但减少展开图像命中且增加准备成本；其他视频不能假设同样体积。需验证总账本包含池、复制和在途，不把双份数据漏算。
- 候选二：图像就绪且仍为最新真实目标时允许受控立即提交，继续保持512MiB、2任务和释放准确性。仅此试验模式获准偏离仅rAF绘制契约；分别统计实际提交、绘制机会及其最终帧，不能把同一次屏幕绘制前被覆盖的提交冒充P-01有效更新，不宣称测得物理屏幕呈现。
- 使用同一现有选中视频/缓存，只读源媒体，不生成新样本或改Eagle库；先有小范围可回退本地提交、模拟正确性检查，再一次合并宿主操作检验滑块与候选。记录准备成本、读取/解码/提交、末次准确性、取代及资源。定向结果不代替完整三轮协议，预算不足不运行整组、不删旧证据。
- 两项分别比较、一次只启用一个，才能辨别原因；不承诺任意不可预测输入在有限内存与处理能力下都零等待。只有实测后才讨论是否调整内存上限或正式架构，并另行记录批准。

实现入口仍是T0测试页。Player默认保持基线，通过显式`baseline`/`compressed-ram`/`ready-submit`实验参数选择互斥候选；无正式产品开关。压缩池上限64MiB且计入512MiB，在首帧就绪前用最多2个受限读取任务预载，不能装下时明确报告部分覆盖及真实初始化成本，不假定所有视频都与本素材同体积。就绪提交保留最新目标同步守卫与每逻辑绘制间隔限次，另在rAF采样最终Canvas身份，以排除被覆盖的提交；采样仍不等于物理屏幕呈现。

增加一次三模式各6秒、目标144次/秒的有界定向对照，固定同一已载入素材/SHA及目标序列，逐轮重建Player、复用已校验磁盘缓存；保留完整精简输入/终态/提交/观察记录，单次合计保存≤2MiB，先预留3MiB证据，含准备成本与资源采样。它不能代替3×30秒正式协议。原40/100MiB协议只允许基线模式并保留原门槛，容量不足不启动、不清旧文件。宿主操作在本地检查后由用户一次完成。

本地执行结果与用户待操作步骤见 [T0记录](report.md)。统一检查不生成媒体；显式 `node scripts/prepare-t0.cjs baseline h264-cfr hevc-vfr vp9-silent` 才准备新缓存，`node scripts/verify-t0.cjs reference …` 只读登记输入和缓存做独立参考，`audio …` 核对已存在PCM；`record-checks` 保存本地检查新证据。`--fresh` 会定向清除已核所有权、无租用的T0该样本缓存后重建，不作默认命令。180秒进程超时及2000帧为T0专项保护，不新增产品输入上限。

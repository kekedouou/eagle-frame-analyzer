# MVP 开发计划与工程执行流程

日期：2026-10-11。状态：3C 文档交付及完成条件自查，待用户最终验收。产品基线为 [product.md v1 及已批准补充](product.md) 的 R-01～R-08、P-01～P-04；实现基线为 [architecture.md v1](architecture.md) 及 A-01～A-03。验证编号、样本与量化口径集中在 [verification.md](verification.md)，本文件只安排任务和交付顺序，避免复制阈值造成漂移。

本轮只落实文档，不创建正式入口、不迁移代码、不运行专项。3C 最终验收与阶段 4 开发授权分别取得；批准本计划不自动批准加载插件、生成样本、写入 Eagle 或删除数据。MVP 是可用首版，既有 PoC 是证据与参考，不能用“仍在实验”替代正式质量要求。

## 正式文件组织与依赖

以下是阶段 4 按需创建的组织，不是当前已有入口。沿用 HTML/CSS/JavaScript、CommonJS、Node 内置模块及现有 FFmpeg/ffprobe，无新框架、构建工具或额外依赖；兼容实际 Eagle Node 16.17.1 / Chrome 108。

```text
plugin/
  manifest.json / index.html      Eagle 的唯一正式入口
  app.js                         启动、plugin.path 与事件接线
  ui.js / styles.css             极简控件与状态展示
  session.cjs                    素材快照、状态及任务所有权
  eagle.cjs                      素材与标注 API 适配
  media.cjs                      媒体分析和 FFmpeg 预处理
  cache.cjs                      受限文件访问、预算、锁与生命周期
  frame-index.cjs                纯源帧编号、PTS 和时间映射
  player.js                      Canvas、Web Audio 与帧调度
  cache/                         将来由运行时管理，忽略入 Git
tests/                           与需求关联的单元、集成及媒体用例
scripts/check.cjs                将来的本地统一检查入口
prototypes/                      原 A/B、S1 与其本机证据保持独立
```

文件按职责平铺即可，不预先创建空文件或多层抽象。正式代码不得依赖 prototypes。UI 只向会话发出操作，不能直接调用 Eagle 数据 API、文件写入或 FFmpeg；只有 Eagle 适配层访问素材/标注 API，只有缓存层负责受限写入、淘汰和删除。媒体准备获得缓存层提供的写入能力，播放器只读登记资源。共享帧索引不访问 UI、磁盘或 Eagle。

正式插件自 T1 起采用自动准备、就绪首帧暂停和单一时间轴；不把样本下拉框、延迟开关、模式切换或测试按钮放进产品。诊断由测试入口与有界记录承担。正式 cache 按已批准架构检查实际路径、非 C、同盘和所有权，不用系统 TEMP 中转媒体缓存。

T1 同时落实用户于 2026-10-11 批准的空格播放／暂停、进度条上方拖动时间数字，以及参考 Eagle 主画面与侧栏结合的极简布局。ui 发出既有会话操作并展示实际已显示帧的时间，不改变媒体/缓存/音频方案；T3 补验标注文字输入时的空格保护，T4 汇总真实体验。常驻秒刻度、悬浮缩略图、完整快捷键系统和复杂视觉/布局框架不列入本次开发；现阶段不固定完整视觉设计或为后续重设计增加抽象层。

## 任务拆分与顺序

顺序为 T0 → T1 → T2 → T3 → T4。每个阶段再拆成一个行为或状态不变量的小任务，避免同时改多个复杂模块后才首次验证。时间和成本用工作量级别表达，不承诺未经依据的日期。

| 节点 | 需求与关卡 | 主要交付 | 工作量与不确定因素 |
| --- | --- | --- | --- |
| T0 核心风险专项 | R-02/03/04/07/08，P-01/02/03，资源停止线关联 P-04 | 同目标序列的调度压力、4K/60fps 首次准备、独立帧参考 | 中～大；取决于读取、JPEG 解码、调度和源时间问题 |
| T1 最早纵向链路 | R-01～04/07/08，R-06 基础边界，P-01～04 早期回归 | 选中 → 自动准备 → 首帧暂停 → 有声播放/空格暂停/拖动时间提示/逐帧；极简主画面与侧栏 | 中～大；宿主接线、源时间映射与声音协作 |
| T2 正式资源与生命周期 | R-01/06/08，P-04，回归 P-01～03 | 复用、淘汰、锁、取消、关闭恢复及窗口切换 | 大；跨进程所有权、故障注入和长时运行 |
| T3 标注纵向链路 | R-05/08，回归 R-01/02/03 | 读取定位、固定显示帧添加、独立读回和未知结果 | 中；真实库授权与 API 结果不确定性 |
| T4 MVP 总验收 | R-01～R-08、P-01～P-04 | 同一候选版本上的完整需求与性能证据 | 中～大；样本补齐、长时采样和人工验收 |

### T0：先验证核心性能与源帧风险

| 项目 | 执行要求 |
| --- | --- |
| 依赖与输入 | 已批准产品/架构及验证协议；选定现有样本、4K/60fps 代表样本和独立帧预期。开始前单独批准具体素材、隔离目录、产物/证据上限、清理范围及宿主操作 |
| 输出与模块 | 最小专项实现及新证据：同一视频最多两个图像读取/解码任务，单个视频预处理；最新目标、播放前瞻与邻帧预取优先级；完整首次就绪计时；独立帧比对。涉及 frame-index、player、media/cache 的最小验证边界，不建完整正式工程 |
| 自动验证 | 用确定目标序列比较常态与慢解码压力；分别记录提交、就绪、请求结束类型、最终帧和无提交间隔。验证同 PTS 源帧、首末帧、VFR 与音频偏移；复核实际生成帧和独立预期，不仅检查内部时间值 |
| Eagle 与人工 | 用户在真实 Eagle 执行约定流程，观察快速往返拖动、末次停住、逐帧及声画。4K/60fps 首次准备从加载入口至播放器就绪记录，缓存命中另报；本地模拟不能替代这些结果 |
| 完成标准 | 达到 verification.md 中 T0 关卡；帧身份无错误，计时边界完整，常态符合性能口径，压力行为与局限清楚。不以已完成请求的低 P95 掩盖长时间没有更新 |
| 风险与回退 | 慢解码饥饿、4K 处理超时、末帧/音频时间不可靠。失败保留原始证据，停止向正式功能扩展并定位瓶颈；需要变更 A-01～A-03 时提交独立变更建议，不降低产品要求 |
| Git 节点 | 每个可复核小改动单独提交；报告对应提交、样本及证据。只有用户明确验收关卡后，才建立本地阶段标签，不提前标记性能通过 |

T0 关卡限定为约定代表样本的正常/压力调度、独立源帧准确性和完整 4K/60fps 首次等待专项，包含执行所需安全预算；不要求提前完成 T2 生命周期、T3 标注或 T4 全矩阵。新增空格与时间提示在 T1 实现验收，不为它们扩展 T0。

## 日常开发、检查与完成标准

每项任务按以下顺序执行：**确认已授权目标与 R/P → 阅读相关边界并分析影响 → 小范围实现 → 适当本地检查 → 适用的真实 Eagle/人工验收 → 保存新证据并更新进度 → 审查 diff → 本地 Git 提交 → 报告结果及下一步边界**。证据和进度先于提交，让版本包含可追溯状态；最终提交号在交付时核对，不为把自身哈希写进同一次提交制造循环修改。

- **粒度**：一个任务围绕一项行为或不变量，例如“旧会话完成解码不能覆盖新素材”。先完成并检查这项再追加范围，不顺手改无关 UI、缓存或文档历史。
- **先写测试的情形**：源帧/时间映射、预算、异步竞态、安全删除、未知写入结果和已复现缺陷，先固定失败条件与独立预期。文案等低影响改动不编写镜像实现的测试。
- **统一入口计划**：将来 `node scripts/check.cjs` 默认进行语法、manifest/DOM 接线、纯单元/模拟集成及文档检查；媒体、性能、宿主证据复核使用显式档位。默认不生成视频、不清共享缓存、不启动 Eagle、不写库。当前不为这份计划编写检查代码。
- **提交前必查**：工作区和 diff、改动是否在授权范围、是否混入 ignored 证据/本机配置/素材、适用测试结果及未执行项、`git diff --check`。仅文档改动使用文档核对，不为凑检查重跑旧实验；Node 24 本地检查不冒充 Node 16 宿主兼容通过。
- **性能回归触发**：读取/哈希/探测、JPEG/音频处理、索引、请求合并、调度/预取、Canvas/Web Audio、预算/淘汰/锁及高频 UI 更新变化时，运行受影响的 P 项；仅改说明或无关低频样式不重测全套。
- **决策变化**：日常实现细节在任务记录说明；改变 A-01～A-03、模块边界、持久格式或测量口径时先独立提议，批准后补 architecture.md 既有决策记录的原因、证据和替代关系，不另造重复 ADR 文件。
- **失败处理**：先保存失败条件、日志、版本与样本，再定位原因；不反复盲改、不删除失败轮次。恢复代码优先 `git revert` 指定提交，不重写历史、不覆盖未提交用户改动，不用切换旧标签破坏当前证据。

任务完成必须同时具备：目标行为已实现、适用检查已通过、真实宿主与人工部分按适用范围确认、证据来源/条件完整、风险和未测项已声明、相关文档/进度更新、diff 范围正确且本地版本可追溯。若缺少必需宿主验证，只能报告“代码/本地检查完成，待宿主验收”，不能称该功能完成。阶段标签固定验收代码，原始证据仍需单独保留。

S1 媒体准备目前明确拒绝重复/倒退 PTS；缺少末帧结束信息时使用名义帧率回退。播放器模拟中“重复 PTS 逐帧可访问”不能证明真实媒体链已支持。正式实现应保留架构要求的整数 PTS/时间基准和每个呈现编号，可靠解决显示区间、末帧和标注时间映射；无法可靠恢复时明确失败，不复制平均帧率猜测。

最小迁移步骤：保留原 prototypes 和证据 → 在获批 T0 中核对高风险算法 → T1 按职责提取一个模块并补对应测试 → 接通最早完整链路 → T2/T3 完成正式所有权与业务边界 → T4 冻结唯一正式候选。测试可复用输入和预期，但正式运行不调用原型源码，不长期维护两套正式实现。旧实验需要复跑时另确认范围，不能把旧清理器作为默认开发检查。

## 关键风险与进入阶段 4 的条件

当前最大风险仍是慢解码无更新、4K/60fps 首次等待、真实源帧/末帧/音频与标注时间映射，其次是正式锁/淘汰/异常恢复、长期资源增长与标注未知结果。已有 PoC 支持核心可行性，没有证明这些正式要求全部满足。

进入阶段 4 前，用户先验收 3C 文档，再明确授权 T0 的样本、隔离输出和证据预算及操作边界；T0 是第一个执行任务。需要新合成样本、真实素材库导入/写入、加载插件或危险故障测试时，仍按根 AGENTS.md 分别授权。T0 未通过不直接铺开 T1～T4，T0 通过也不自动取得后续阶段授权。
